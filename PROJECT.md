# PocketOga

## 1. What PocketOga is

Voice-first AI bookkeeping assistant for Nigerian market traders, on WhatsApp and the web. Understands English, Pidgin and money talk like 15k.
Trader speaks or types a note, the AI proposes ledger entries, plain code checks them, the trader taps confirm, entries land in a hash-chained ledger.
Meta Global AI Developer Hackathon, Indie track. Submission planned for the evening of Tue 3 Nov 2026.

## 2. Core rules

- The AI only proposes. Plain code checks every number. The trader confirms every entry. Nothing is saved without a tap.
- Append-only ledger: per-shop chain, `seq` from 1, `prev_hash` links, SHA-256 over `HASHED_FIELDS` (exact, in order): `["shop_id", "seq", "type", "amount_kobo", "customer", "item", "quantity", "unit", "created_at", "corrects_id", "prev_hash"]`. SQL triggers abort UPDATE/DELETE.
- Money in integer kobo, never floats. Proposal entry types: sale, payment, restock, expense. The model, hints and forms say `purchase`; code normalizes it to `restock` before anything is checked or stored. Stored corrections use type `correction`. No `debt` type exists.
- Record once: voice, text, hint and form all run the same propose, check and confirm flow. Every proposal carries a `source` (voice, text, form) and code-computed `effects` (destination view, stock movement, cost unknown); ledger rows look identical whatever the path.
- Corrections are new entries (`corrects_id` link, same shop); reasons live in `corrections_log`, never in the ledger or hash.
- Checks split into BLOCKING (Save locked, at most two one-line questions: missing/unreadable amount, missing customer, contradictory numbers — total, paid and stated remainder do not add up — note says each but the amount was read as a total, payment above known owed, heard amount at the wrong magnitude (no spoken number within 2x), two equally-close customers, plus the model's own question echoed only when code asked nothing and it is not a total-vs-each question, which resolves softly) and SOFT (one "PocketOga assumed:" block, Save enabled, Fix one tap away: customer/product match, new customer/product, expense category, unit spelling, promise date, negative stock, unknown cost, second-opinion customer/entry-count/promise-date disagreements, no-debt payments, remain-vs-balance mismatches, 5x usual-price "Is this right?", exact-duplicate merge lines, balance-filled remain payments). Exact-duplicate entries merge into one with a soft line — a payment is never duplicated in a proposal. "The remain/balance/rest" with no stated amount fills from the customer's recorded balance (soft line); unknown/zero balance still blocks as missing. Correction cards never claim "New customer".
- Debt statements with no sale details ("Ada dey owe me 5k") record as one sale of unknown item (customer + amount known, owed; stock unchanged), with zero questions — never a question, never skipped.
- Confirm is idempotent (`alreadyConfirmed`); proposals expire after 30 minutes.
- Passwordless login: WhatsApp `dashboard` issues a one-time code (hash stored, 10-minute expiry, one use, 5 per number per hour); the code exchanges for a shop-scoped session token (expiring, revocable); every non-demo route needs a live token for exactly that shop; the demo shop stays public.
- Photos: the AI classifies the type and extracts fields; code runs every check; the trader confirms; raw photos are never stored.
- Daily summary: opt-in evening message computed by code from the ledger (no model, no invented numbers) — today's sales, collected, expenses, estimated profit plus the one most important thing (due/overdue promise, big new debt, low stock, stale transfer, else all calm); skipped on days with nothing. Once per shop per day at its hour.

## 3. Stack and files

Backend: Node ESM (`.mjs`), `node:http`, `node:sqlite`, `node:crypto`, `node:test`. Zero runtime dependencies; `sharp` is a devDependency used only for landing photos.

- `ledger.mjs` — append-only chain, `verify`/`verifyChain`, `appendCorrection`, `recordCorrectionReason`.
- `proposals.mjs` — draft proposals; drafts never touch the ledger.
- `voice.mjs` — propose/fix/confirm/reject/get plus `proposeFromForm` (no model call); model-output validation, price basis (`each`/`total`/`unclear`), stated-remainder, honorific-aware customer matching (titles stripped, taken/new soft, two-candidate ask), soft product matching, overpayment block, hint handling, code-computed effects, dev-only step timings (`POCKETOGA_TIMING=1`).
- `money.mjs` — `parseNaira` (15k, N2,500, number words), `nairaToKobo`, `formatKobo`.
- `model.mjs` — Meta API client (text, audio, image) plus the mock client all tests use.
- `photos.mjs` — photo pipeline and Alert Guard checks, plus the `payment_checks` store (extracted fields only, never raw photos).
- `whatsapp.mjs` — webhook processing, commands, voice notes, Save/Fix/Reject buttons, dedupe, allow-list.
- `server.mjs` — main API plus webhook-only listener; `buildDeps(env)` wires stores without sockets. Serves `web/dist` on the same origin (SPA fallback, hashed assets immutable, index no-store, gzip when accepted, `/api` prefix stripped for dev-proxy bundles); `GET /health` returns `{ok: true}` with no auth. State under `DATA_DIR` (default `./data`, created when missing): SQLite file is `DATA_DIR/pocketoga.db` unless `LEDGER_DB` names another path. Listens on `PORT` bound to `0.0.0.0`; the webhook-only listener starts only when `WEBHOOK_PORT` is explicitly set to something else (local tunnel setup — leave it unset on Render, where one URL serves app + webhook). Graceful SIGTERM/SIGINT shutdown (finish in-flight, back up, close the DB).
- `demo-seed.mjs` — `seedDemoShop(deps)` reseeds the demo shop with the same 15 fake entries + 3 promises as `web/scripts/seed-demo.mjs`, in-process via propose/confirm (no model, no keys, milliseconds); skips when the demo ledger is non-empty. `backup.mjs` — 10-minute + shutdown SQLite backup via `VACUUM INTO` into `DATA_DIR/backups` (last 7 kept, log lines carry no data); `restoreIfMissing` brings back the newest backup on boot when the main file is gone. `deploy.test.mjs` — DATA_DIR paths, `/health`, reseed, backup round-trip, static serving.
- `auth.mjs` — `AuthStore`: login codes (hash, expiry, one use, rate limits) and sessions (verify, revoke).
- `messages.mjs` — every user-facing WhatsApp string (cards with destinations and effect lines, debts, chase, report, stock, profit, expenses).
- `debts.mjs` — balances (oldest-first), chase ranking, Lagos-day helpers. `promises.mjs` — promise store, code-resolved relative dates (Africa/Lagos, weeks start Monday; unresolvable means "No pay date set", never a question), kept/broken. `leak.mjs` — Money Leak Report, including unconfirmed transfers.
- `products.mjs` — catalog (auto-created on confirm, trader-set prices, stock from ledger, low at ≤3). `customers.mjs` — directory (phones + consent, never in the ledger).
- `secondopinion.mjs` — Baseten re-read of the note plus code comparison; stats in `second_opinions`.
- `summary.mjs` — daily-summary opt-in store (`summary_settings`: shop, number, enabled, hour, last_sent_date, last_inbound_at, pending), code-only day figures plus the one most important thing, once-a-minute scheduler tick.
- `profit.mjs` — profit and expenses per period (Lagos time), weighted-average COGS (`costBasisByProduct`, shared with the catalog), bucketed series.
- `scripts/gen-landing.mjs` — generates the 12 landing photos with Muse Image. `scripts/optimize-landing.mjs` — resizes/re-encodes them to ≤200 KB (originals kept in `_originals/`).
- Helpers: `preview-messages.mjs`, `preview-debts.mjs`, `preview-profit.mjs` (print cards in terminal); `smoke-live.mjs` (manual propose-only run); `tamper-demo.mjs` (local verify demo); `audio-test*.mjs`, `baseten-test.mjs` (manual model probes); `note*.wav` (sample audio for the probes). `scripts/latency-check.mjs` runs 12 fake notes through the real pipeline and prints per-step timings plus the question rate (mock by default; real model with `META_API_KEY`). `scripts/accuracy-run.mjs` sends every wav in `test-audio/expected.json` 3x through the real WhatsApp voice-note path (`propose` with `{ audioPath }`, real Meta client, nothing confirmed) in `--seeded` (default: known customers, debts, prices, stock) and `--empty` modes (either alone via its flag, both by default), scoring customers by strict whole-name equality (titles/spacing/case forgiven, no substring matches), consistency on normalised item names (case, singular/plural, garri/gari), and reporting per-note/overall type/amount/customer/count correctness, consistency, and the silence metric (fully correct vs wrong-but-flagged vs silently wrong, the headline), writing summary tables to `accuracy-results.md` (regenerated each run; never commit `test-audio/`). `scripts/compare-transcribe.mjs` A/Bs direct audio extraction against Muse Voice Transcribe on real WAVs (keys required, no mock). `scripts/repeat-check.mjs` sends 3 fake text notes 5 times each through the real propose() and prints distinct-result counts (keys required, nothing confirmed). `test-notes.md` is the manual test log.

Web (`web/`, React 18 + Vite 5 + Tailwind 4 PWA): `src/screens/` (Record, ConfirmCard, Ledger, Debts, Report, Money, Sales, Expenses, Products, Customers, Settings, Accuracy, Landing), `src/landing/` (marketing page), `src/api.js` (backend client, incl. ledger corrections), `src/format.js` (₦/kobo), `src/shop.js` (open shop on device), `src/wav.js` (mic to WAV). Landing photos in `public/landing/photos/*.webp` (SVG fallback for non-shop slots). `web/scripts/`: `seed-demo.mjs` (fills demo shop via real propose/confirm), `mock-contract.mjs` (dev-only stand-in), `check-no-mock.mjs`, `check-landing-copy.mjs`, `check-landing-images.mjs`.

Run: backend `node server.mjs` (`PORT`, `DATA_DIR`, optional `LEDGER_DB`); web `cd web && npm install && npm run dev` (`/api` proxies to localhost:3000, `BACKEND_URL` moves it); production web bundle built with `VITE_API_BASE=""` so it calls the same origin (dev-proxy `/api` bundles also work — the server strips the prefix); tests `npm test`; local tunnel points at 3001 only (Render: one URL serves app + webhook). Deploy: root `Dockerfile` + `render.yaml` (one Docker web service, free plan, `healthCheckPath: /health`), `README.md` "Deploy" has the steps; `.env.example` lists every variable by name only.

## 5. WhatsApp

- Main server on `PORT` (default 3000, local only); webhook-only listener on `WEBHOOK_PORT` (default 3001, 404s everything but `/webhook`). Tunnel points at 3001 only. `WEBHOOK_PUBLIC_ONLY=1` hides non-webhook routes from tunnelled traffic.
- POST signature: HMAC-SHA256 over the raw body compared (timing-safe) with `x-hub-signature-256`, secret `WHATSAPP_APP_SECRET`. GET handshake via `WHATSAPP_VERIFY_TOKEN`. Replies via Graph API (`WHATSAPP_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`).
- Only `WHATSAPP_ALLOWED_NUMBERS` (comma-separated) are served; anyone else gets a not-registered reply. Each sender maps to a shop (`wa-` + 16 hash chars). Duplicate deliveries are deduped; secrets and full numbers are masked in logs.
- Exact commands, matched before the note flow (case-insensitive): `who owes`, `chase`, `report`, `stock`, `profit`, `profit week`, `profit month`, `expenses`, `balance <name>` — all answered without the model — plus `fix last <text>`, which reads the corrected note with the model and shows a correction card with Save/Fix/Reject (bare `fix last` explains the usage), and `dashboard`, which texts back a one-time login code (10-minute expiry, one use, 5 per number per hour). Evening-summary opt-in: `summary on`, `summary off`, `summary 7pm` (5 to 11 PM, default 8 PM Lagos) and `summary now` (today at once, no opt-in needed). Free text inside 24 h of the trader's last message, else the `WHATSAPP_SUMMARY_TEMPLATE` template; with no template the text waits and arrives as "Your summary from last evening" on the next inbound. `summary now` and `GET /summary/preview` serve the logged-in shop only.
- Voice notes: media is downloaded immediately, converted with ffmpeg to 16 kHz mono WAV, then sent to the audio model; clear fallback messages when ffmpeg or conversion fails. An immediate "Got it, checking…" ack is sent before the slow steps; the confirm flow is unchanged. Text/voice notes get proposal cards with Save/Fix/Reject buttons; per-sender fix state tracks what Fix refers to.
- Photos: the trader sends a JPG/PNG; Alert Guard classifies it, extracts fields and runs code checks, then shows a result card ("warning signs found" / "no warning signs found") with Save/Fix/Reject. Save records an unconfirmed transfer plus a follow-up card with the "I saw it in my bank" button (four buttons can't fit one WhatsApp card); the tap marks it confirmed (`POST /photo-checks/:id/bank-confirm` is the same tap for the web Check alert screen; `GET /photo-checks/unconfirmed` lists them; report transfer items carry the same `id`). Fix on a photo card asks for the photo again. Never "verified".

## 6. Models

- Meta Model API (`https://api.meta.ai/v1`, key `META_API_KEY`): `muse-spark-1.3` for text extraction, `muse-spark-1.2` for audio input (`input_audio` WAV part), `muse-spark-1.3` for photos (`image_url` part, JSON contract in `PHOTO_SYSTEM_PROMPT`): the model classifies the photo type and extracts fields, code runs every check. `reasoning_effort: minimal` (docs-verified floor, re-checked 30 Oct 2026; `none` returns 400, no thinking-budget parameter exists), compact-JSON-only replies, 2000 output tokens with one automatic double-budget retry on `finish=length`. Deterministic sampling (docs-verified 30 Oct 2026): `temperature: 0` + fixed `seed: 7` on text/audio/photo calls (one shared path); `top_p` untouched per docs (temperature or `top_p`, never both; `top_p: 0` is a 400); `seed` is deprecated but accepted, best-effort, determinism not guaranteed. Docs caveat: Muse Spark performs best at the defaults — revert temperature to 1 if quality drops. The prompt's types are sale/payment/purchase/expense and its expense categories include fuel and data; debt lines with no sale details read as one sale of unknown item (same rule in the minimal second-opinion prompt); an optional hint rides along as a likely type only. The shared audio/text prompt carries a compact trader glossary ("don pay"/"e pay"/"dem pay" = payment received, never a sale even with "buy" later; "buy"/"collect"/"take" + goods = sale; "dey owe me" = debt; "remain"/"balance" = remainder; e/wey/don/dey/abeg; 5k/forty-five hundred = 4,500/two k = 2,000; mudu/paint/derica/congo/bag/carton/crate/tuber/bunch) plus the hearing rule (heard is exactly what was said, `[unclear]` marks gaps, unclear amounts ask, code-computed totals never appear in heard). Both audio and text calls also receive the shop's known customers/products (top 20 each) as exact-spelling context, so "Ada" survives transcription. Glossary also covers "don pay the remain X"/"pay the balance" (payment of X, never a sale), first-person "I buy/I bought" (purchase for the shop, customer null), and matching names against known customers before accepting a new one. Known-names context also carries balances owed ("Bola owes 2500"); "the remain/balance/rest" with no amount reads as the balance owed, a spoken amount always wins. Code-side number checks: no-debt payments and remain-vs-balance mismatches (soft), 5x usual-price "Is this right?" (soft, Save enabled), heard-vs-amount magnitude mismatch (blocking). All suites use the mock client.
- Second opinion: a Baseten text model (`BASETEN_API_KEY` + `BASETEN_MODEL`, `https://inference.baseten.co/v1/chat/completions`) re-reads the note's heard text with a minimal extraction prompt (4 s cap per attempt plus one network-only retry, started in parallel with the main read; 1000 max output tokens; reasoning channels stripped before parsing; deterministic sampling `temperature: 0` + `seed: 7`, OpenAI-compatible names — the Meta docs do not cover the Baseten host); plain code compares types, customers, amounts, quantity, unit, price basis, promise and expense category (amounts normalised across crossed each/total readings first, recorded as `amount-normalised`). Only amount, customer, entry-count and promise-date disagreements may reach the trader — amount asks at most one question merged with any code question, the other three are soft assumption lines — while category, unit and the rest record in the stats only; entries are never changed; stats go to `second_opinions`; skipped silently without keys. Dev-only per-attempt log (`POCKETOGA_TIMING=1`): status, finish reason, empty flag, reasoning/output tokens, never the note text.
- Model calls: per-kind timeouts (30 s text, 90 s audio, 30 s photo) with one retry on transport errors, timeouts, 429 and 5xx; other 4xx fail fast. Empty/unparseable output degrades to a confused card — voice keeps "I no hear am well", text gets "I no understand that note" (a text note never says it wasn't heard). Audio with zero entries retries once silently with the same input; still empty shows "I no catch that, say am again" (text never retries, wording unchanged). Length cutoffs salvage complete JSON or retry once with double budget; two failures show "Something went wrong on my side, please send it again." Dev-only per-call log (`POCKETOGA_TIMING=1`): attempts, status, finish reason, in/out/reasoning tokens, content length, never the note text.
- Landing photos: Muse Image (`muse-image-1.0`, `POST /v1/images/generations`, webp out). `scripts/gen-landing.mjs` generates 12 shots (key from `META_API_KEY`); `scripts/optimize-landing.mjs` fits each under 200 KB.

## 8. Working rules

- Keys live only in `.env.local` (never opened, never printed, never committed): `META_API_KEY`, `BASETEN_API_KEY`, `BASETEN_MODEL`, `WHATSAPP_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_APP_SECRET`, `WHATSAPP_VERIFY_TOKEN`, `WHATSAPP_ALLOWED_NUMBERS`, `WHATSAPP_SUMMARY_TEMPLATE`, plus `PORT`, `WEBHOOK_PORT`, `WEBHOOK_PUBLIC_ONLY`, `LEDGER_DB`.
- Fake data only; no real trader data while coding. Per-shop isolation on every route.
- Muse Code owns the backend, Claude Code owns `web/`; plain screens may go to either tool, but never both on the same files at once.
- Commit only when `npm test` is green and `git status` shows no `.env`, `.db` or `_originals` files.
